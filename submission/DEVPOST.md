## One-line pitch

An offline, multi-turn shopping copilot that routes committed buyers and exploratory
shoppers differently, preserves and rewrites typed intent over time, learns which
questions a customer will answer, and explains why products ranked where they did.

## The problem

Product search is easy when a shopper already knows the catalog's taxonomy and hard
when they speak like a person: “something for outdoor work,” “actually, make that a
leather belt,” or “I don't mind about colour.” The challenge is to find a hidden item
in a frozen 50,000-product catalog within ten turns while balancing coverage,
ranking, and time-to-convergence.

## What we built

The runtime pipeline is:

`intent/state update → routed in-memory retrieval → interpretable scoring → small
linear reranker → confidence-based commit → value-of-information question`

- Buying uses a narrow, high-precision shelf route; browsing widens and diversifies.
- Retrieval fuses category, mined semantic vocabulary, lexical postings, and BM25.
  The semantic route is a catalog-mined word-to-shelf association map with a trigram
  fallback, not a vector-embedding index; the reranker is a linear model, not an LLM.
  We name them that way deliberately — see *Honest scope* below.
- Typed slots accumulate, supersede by attribute, reset by product epoch, and retain
  retracted evidence at low weight instead of deleting history.
- Over-general requests trigger a retrieval cutoff and structured clarification.
- Answerability and bounded profile memory adapt online without pretraining on the
  evaluator.
- Runtime uses only Python's standard library: no foundation model, no external
  model or API call, no network, no GPU, and no token cost during scoring. The one
  learned component is a small linear reranker whose weights are fitted offline on
  sessions 1-100 and committed to the repository.

## Why the measurement is different

We keep four views of quality because one leaderboard number hides distinct failure
modes:

| View | What it tests | Current result |
|---|---|---:|
| Official public set | organizer contract | 0.916125 score; HR@10 1.000; MRR 0.773417; MTTC 1.795 |
| Shadow | retrieval without three simulator artifacts | 0.89854; retrieval MRR 0.6768 |
| Snapshot MRR | reranker ordering with pool/state fixed | +0.0202 dev; +0.0347 holdout |
| Adversarial matrix | category/scaffold/constraint/paraphrase drift | `analysis/bench.json` |

Every ranking experiment is fitted on sessions 1–100 and validated on 101–200.
Changes must improve both halves or ship through a documented product-behavior door.
Failed experiments stay in the ledger instead of disappearing.

## V3 hardening

- Shared NFKC and typographic-punctuation normalization now protects exact shelf,
  phrase, and dialogue-act channels while preserving historical ASCII-hyphen
  semantics.
- Product switches reopen product-bound questions while retaining person-level
  budget/brand history. Explicit restarts begin a genuinely clean product epoch.
- Full-public output is stable under `PYTHONHASHSEED=1,2,777`; tests block sockets,
  block post-construction file access, and AST-scan runtime imports.
- Two plausible hedge experiments were built and declined: category terms did not
  improve pool recall, and rival-shelf slate reservation did not clear its required
  category-axis confidence interval. Measurements are in
  `analysis/improvement_plan_v3_results.json`.

## Feasibility and cost

The catalog is indexed once in memory and never mutated. Runtime token usage is
0 prompt / 0 completion, estimated scoring model cost is **$0.00**, and the evaluator
works with socket creation disabled.

Measured on a quiet arm64 macOS host, Python 3.9.6, 299 serial turns per route in a
fresh process (2026-08-31, `analysis/resource_probe_v6_baseline.json`):

| Route | p99 | max | peak RSS |
|---|---:|---:|---:|
| exact | 5.178 ms | 5.460 ms | 781.2 MB |
| hedged | 33.566 ms | 34.647 ms | 788.9 MB |

Zero of 299 observations reached the 50 ms engineering canary on either route. Two costs
we would rather state than bury: **agent construction takes 17.069-17.678 s** (a one-off
index build, excluded from turn latency), and **peak RSS is about 789 MB**, because the
whole catalog is resident. A run taken while the machine was loaded produced one 56.8 ms
hedged turn, so 50 ms is a canary, not an SLA. Fresh resource numbers and the evaluator
checksum are generated by `python3 -m tools.audit` into `analysis/operational_audit.json`.

## Who this is for, and what it changes

- **The shopper** who cannot name the shelf. Someone who says "something for outdoor
  work" does not know the catalog says `Accessories Belts`. The agent converts a
  median session in 1.795 turns, and every returned slate carries the reason a product
  is on it, so the shopper can correct the wrong assumption rather than restart.
- **The shopper who changes their mind mid-conversation.** "Actually, make that a
  leather belt" rewrites the typed slot instead of stacking a second constraint on the
  first. On the 30 intent-override sessions the agent reaches HR@10 1.000 at MRR 0.864.
- **The retailer.** Every question the agent asks is chosen by expected value of
  information *and* by whether this shopper has answered that kind of question before,
  so the agent stops interrogating people who do not answer. Runtime is stdlib-only and
  deterministic: no per-query inference cost, no vendor dependency, no PII leaving the
  process.
- **The team operating it.** Ranking changes ship only if they clear both a fitted half
  and a held-out half, and declined experiments stay in the ledger. That is the part
  that makes the system maintainable rather than merely scoring well once.

## Honest scope

We would rather be precise than flattering:

- The `dense` route is **not** vector similarity. It is an offline, catalog-mined
  word-to-shelf association map with a trigram fallback (`src/semantic.py`). We tried a
  real GloVe-50 vector route; it moved the official score by 0.00000 and *lost* 0.04 of
  top-1 shelf resolution on the axis it was built for, so it was reverted rather than
  shipped for the label.
- The ranking stage exists twice. The default is a **linear model** (`src/rerank.py`);
  an **LLM semantic ranking stage** (`src/llm_rank.py`) is real, reachable code behind
  `TECHJAM_LLM_RERANK=1` + `AIAND_API_KEY`, off by default, with a tested total fallback
  to the linear order on any failure. It is off because we measured the ordering and it
  lost: **+0.0025 dev / −0.0061 holdout** at its best blend, **−0.172 / −0.249** raw,
  against the linear model's +0.0207 / +0.0354 (D11, `analysis/llm_rerank_probe.json`;
  the live demo run is `analysis/v8_w2_llm_stage.json`). One model, one prompt, one
  placement — evidence about *this* ranking stage, not a verdict on LLMs generally.
- Hard constraints are **soft-scored with large weights**, not filtered. This is
  deliberate — a hard filter on a mis-parsed constraint empties the pool — but it means
  "hard constraint" is a ranking statement, not a guarantee.
- Retracted evidence supports **two modes**: the default **down-weights the superseded
  slot to 0.08** (`src/state.py`); `P_SUPERSEDE=erase` deletes it from the state
  entirely — the literal slot erasure the brief names. Measured on the shipped agent,
  erase costs **0.00275 of official score and one intent-override hit**, so decay stays
  the default with the cost quantified (`analysis/v8_w3_erasure.json`).
- The over-generality cutoff is **pre-retrieval and real**: pool breadth is estimated
  from bucket sizes before any product is scored (`CommitPolicy.pre_cutoff`); when the
  estimate exceeds the overload threshold and no discriminating constraint is filed, a
  bounded representative sample is scored and the agent goes straight to the question.
  The post-retrieval confirmation (`CommitPolicy.cutoff`) remains as the safety net.
  Measured at zero cost — score and transcript byte-identical
  (`analysis/v8_w4_cutoff.json`).
- `LongTermMemory.recall()` (`src/memory.py`) **is consumed** at two production sites:
  a profile shape's recalled shelves enter the capped ranking tie-break, and its recalled
  asked/answered history seeds question selection as a bounded prior that settles
  exact-value ties between measured question values. The official harness simulates
  isolated single-user sessions, so its measured effect here is exactly zero and the
  public transcript is byte-identical — the loop is real, the interlocutor gives it
  nothing to amplify (`analysis/v8_w1_longterm.json`).

## Built with

**Languages** — Python 3.9+ (verified on 3.9.6, 3.10.12 and 3.13).

**Libraries and frameworks** — none. `requirements.txt` is empty by design: the runtime
uses only the Python standard library (`json`, `re`, `math`, `collections`,
`dataclasses`, `unicodedata`, `heapq`, `statistics`). No numpy, no PyTorch, no
scikit-learn, no sentence-transformers, no vector database, no web framework. Tests run
on stdlib `unittest`.

**APIs and models at runtime** — none on the default path. No foundation model, no
hosted API, no model weights downloaded, no network socket opened (the test suite blocks
socket creation and AST-scans runtime imports to keep it that way). The only learned
artifact is a small linear reranker fitted offline and committed as plain JSON. An
optional LLM ranking stage (`src/llm_rank.py`, moonshotai/kimi-k3 via AI&) is reachable
behind `TECHJAM_LLM_RERANK=1` + `AIAND_API_KEY`; it is off by default because we measured
it and it lost. The organizer's 2026-08-31 FAQ permits network and external APIs and does
not require an offline fallback — staying offline by default is our engineering choice
(determinism, zero credentials, $0, no vendor availability risk), not a rule we are
obeying.

**AI used at development time** — an LLM assistant (Claude) was used to write and review
code, author test material, and draft documentation. Everything it produced is either a
committed source file, a committed asset, or a recorded measurement. None of it is
invoked at runtime, at build time, or during scoring; reported token usage is 0 prompt
and 0 completion on every turn of every session.

**Development tools** — git and GitHub for version control, `unittest` via
`run_tests.sh` for the 540-test suite, the organizer's `evaluator/local_evaluator.py`
for official scoring, and our own harnesses in `tools/` (adversarial paraphrase matrix,
shadow evaluator, snapshot-MRR replay, near-duplicate shelfbench, resource/latency
probe, provenance and checksum auditors). Editors: VS Code. OS: macOS (arm64) and
WSL2/Ubuntu (x86_64); both are recorded in the resource-probe provenance.

## Data and assets

- **Dataset** — the frozen 50,000-product catalog shipped in the TechJam participant
  kit, derived from **Amazon Reviews 2023** (McAuley Lab, UCSD;
  https://amazon-reviews-2023.github.io/), category `Clothing_Shoes_and_Jewelry`, joined
  on `parent_asin`, text and structured metadata only. See `DATA_ATTRIBUTION.md`. The
  catalog is read-only: never mutated, never extended, no synthetic identifiers added.
  We do not redistribute it — the README Quick Start points at the organizer's release
  and pins its sha256.
- **Assets we generated** — `assets/v6_shelf_aliases.json` and
  `assets/v6_shelf_mnn.json` (mined from the frozen catalog, each with a committed
  provenance manifest), the committed linear-reranker weights, and the dev/holdout
  session splits. All are regenerable from committed code plus the frozen catalog.
- **Third-party assets** — none. No stock media, no pretrained weights, no fonts, no
  icons, no external images.
- **Not included** — no images, video, credentials, private organizer labels, or private
  holdout sessions.

## What we would do with more time

1. Validate against humans rather than the simulator. Every claim here is simulator-
   bound; the adversarial matrix narrows that gap but does not close it.
2. Attack shelf *disambiguation* — the one axis we could not move — with signals the
   catalog does not currently expose, since we showed the evidence needed to separate
   near-duplicate shelves is identical on both sides.

## Limitations

The public simulator states the catalog shelf verbatim, cannot answer several easy
clarification questions, never reveals budget, and terminates as soon as the target
is shown. We therefore report artifact-free and adversarial measurements next to the
official score. Long-term memory's `recall()` is consumed by the profile tie-break and
question selection (closed-loop), though the isolated-session harness gives it nothing
to amplify — see *Honest scope*. 78.9% of products lack price metadata, which is
why budget is the constraint we can least often honour.
